# Повторный аудит надёжности перевода — 6 сентября 2026

## Вывод

Переводы нельзя считать безотказными. В проекте есть полезная основа: несколько провайдеров,
отложенный запуск резервов, отмена проигравших, circuit breaker, повторы, дедупликация и LRU-кэш.
Однако обнаружены воспроизводимые дефекты и реальная несовместимость защитных маркеров с двумя
ответившими сервисами. Количество включённых провайдеров заметно завышает фактическое число
работающих независимых резервов.

В рамках аудита код продукта не исправлялся. Добавлены этот отчёт, диагностические скрипты и
результаты их выполнения. Предыдущий [аудит от 4 сентября](RELIABILITY_AUDIT.md) сохраняется как
история; его утверждения об устранении проблем не означают полной надёжности текущей версии.

## Что и как проверено

- Прочитан путь content script → Translator → racing provider → runtime messaging → service worker,
  реализации семи публичных сервисов, proxy, настройки, защита текста, вывод результата и тесты.
- `npm ci` установил зависимости из lockfile.
- `npm run typecheck`, `npm run lint`, `npm test`, `npm run build` прошли. **62 unit-теста, 14 файлов.**
- После установки Chromium прошёл `npm run test:e2e`: **1 браузерный тест**. Он проверяет загрузку
  расширения, настройки и жизненный цикл карточки, но не утверждает успешный перевод текста.
- Шесть диагностических сценариев воспроизвели поведение текущего кода с управляемыми ответами.
  [Скрипт](audit-2026-09-06/probes.ts), [результаты](audit-2026-09-06/reproductions.json).
- Семь провайдеров проверены на двух коротких синтетических фразах `en→ru`.
  [Скрипт](audit-2026-09-06/live-probe.ts), [полные ответы и HTTP-статусы](audit-2026-09-06/live-results.json).
  Тексты пользователя, реальные твиты, токены аккаунтов и ключи не использовались.

Сетевая проверка выполнена с хоста аудита через Node fetch около 15:19 UTC. Для Bing, TartuNLP,
LibreTranslate, Lingva и Apertium вызвана реализация проекта; для Google и MyMemory воспроизведены
запросы background handler. Это **снимок доступности**, не измерение uptime, не нагрузочный тест
и не проверка запросов внутри Chrome MV3. IP, браузерные заголовки и окружение могут менять результат.
По этим двум фразам нельзя оценить процент отказов или выбрать лучший движок по качеству.

Повторить диагностику после установки зависимостей:

```powershell
node node_modules/vite-node/vite-node.mjs docs/audit-2026-09-06/probes.ts
node node_modules/vite-node/vite-node.mjs docs/audit-2026-09-06/live-probe.ts
```

Второй скрипт обращается к внешним сервисам; оба обновляют свои JSON-отчёты. Первый скрипт
подтверждает именно существующие дефекты, а не задаёт желательное поведение будущей версии.

## Реальные ответы провайдеров

Обычный текст: `The team will release the update tomorrow.`

Текст с защитой: `The team will release ⟦TT0⟧ tomorrow.`

| Провайдер | Обычная фраза | Фраза с маркером |
| --- | --- | --- |
| Google free | HTTP 429, 504 мс | HTTP 429, 512 мс |
| Bing web | HTTP 401 после обновления авторизации, 3515 мс | HTTP 401, 2553 мс |
| TartuNLP | Перевод, 387 мс | Ответ за 335 мс, маркер повреждён |
| MyMemory | Перевод, 944 мс | Ответ за 556 мс, маркер повреждён |
| LibreTranslate, текущие 5 зеркал | Нет пригодного ответа, 1633 мс | Нет пригодного ответа, 1416 мс |
| Lingva, текущие 7 зеркал | Нет пригодного ответа, 2554 мс | Нет пригодного ответа, 2696 мс |
| Apertium | Таймаут около 3 с | Таймаут около 3 с |

LibreTranslate/Lingva дали сочетание HTTP 403/404/500, HTML вместо JSON и сетевых ошибок.
Эти конкретные зеркала не следует объявлять навсегда недоступными по одному запуску.

TartuNLP вернул `Завтра команда выпустит TT0.` — исчезли обе скобки маркера.
MyMemory вернул `⟧ Завтра команда выпустит ⟦TT0.` — скобка перемещена.
Оба результата отвергаются `hasIntactProtectedMarkers`. Итого в этой выборке:
**2 из 7 дали перевод обычной фразы, 0 из 7 дали пригодный ответ для фразы с маркером.**
Это количество ответов на конкретные пробы, не вероятность успешного перевода.

## Подтверждённые проблемы по приоритету

### P1 — схема защиты текста отсекает реально работающие резервы

Места: `src/translation/text-protection.ts:417`, `src/translation/result-validation.ts:12`,
`src/translation/providers/racing.ts:141`.

Маркерами заменяются не только адреса и тикеры, но также числа, emoji, переносы строк и большой
словарь терминов. Поэтому проблема касается обычного содержимого твитов, а не только редких
специальных строк. Живая проверка показала повреждение маркера у обоих доступных резервов.
Повтор того же защищённого запроса не устраняет несовместимость протокола защиты.

Что изменить: валидировать формат защиты на корпусе твитов для каждого провайдера; использовать
поддерживаемую конкретным API защиту HTML/XML/терминов, где она документирована. Для остальных
нужен резервный перевод текстовых участков с локальной сборкой защищённых значений. Разбиение
может ухудшать контекст, поэтому его качество также нужно измерить. Простая замена скобок без
проверки не является доказанным исправлением. Ослаблять проверку так, чтобы терялись адреса и
числа, нельзя считать решением.

### P1 — исходный язык подменяется английским

Места: `src/translation/translator.ts:69`, `src/background/free-providers.ts:114`,
`src/background/free-providers.ts:136`, `src/background/index.ts:93`.

Translator не передаёт исходный язык. TartuNLP, MyMemory и Apertium при его отсутствии используют
`en`, а TartuNLP дополнительно записывает это предположение в `detectedLanguage`.
Диагностика подтвердила: японская фраза отправляется с `src: "eng"`, результат маркируется `en`.
Если такой сервис вернёт изменённый, но ошибочный текст быстрее остальных, он может выиграть гонку.

Что изменить: определить язык по исходному тексту до маскирования, передавать его всем движкам,
разделить «обнаруженный» и «предполагаемый» язык. При неопределённости допускать только сервисы
с автоопределением. Проверять поддерживаемую пару до отправки. У TartuNLP список пар доступен
через `GET /v2`; исходный язык обязателен в контракте. [Официальная схема TartuNLP](https://api.tartunlp.ai/translation/openapi.json).

### P2 — таймаут и отмена перестают защищать чтение тела ответа

Место: `src/background/free-providers.ts:265–282`.

`fetchWithTimeout` возвращает `Response`, очищает таймер и удаляет связь с родительским сигналом.
Однако `response.json()`/`response.text()` вызываются после возврата из функции. Когда заголовки
пришли, а тело зависло, таймаут уже выключен и отмена проигравшего запроса не доходит до fetch.
Диагностический сценарий подтвердил `parent.aborted === true`, но сигнал fetch остался активным.
После искусственного завершения тела функция даже приняла ответ после отмены.

Это затрагивает Bing, TartuNLP и Apertium. Runtime-обёртка может завершить ожидание контент-скрипта
по своему таймеру, поэтому из дефекта не следует бесконечное зависание всей карточки; проблема
остаётся в сетевой работе service worker и его ресурсах.

Что изменить: держать таймер и связь отмены до полного чтения и разбора ответа; проверять уже
отменённый сигнал перед началом запроса. Добавить тест сервера, который отдаёт заголовки и задерживает тело.

### P2 — плохое зеркало отменяет хорошее до проверки перевода

Места: `src/background/free-providers.ts:161`, `src/background/free-providers.ts:182`,
`src/background/free-providers.ts:221–238`.

Внутренняя гонка зеркал принимает любой непустой ответ, отменяя остальных. Внешняя гонка только
после этого проверяет неизменённый оригинал и маркеры. Воспроизведение: первое зеркало возвращает
`Hello`, второе могло вернуть `Привет`; итог — отказ всего LibreTranslate, второе зеркало не запущено.
Для Lingva применяется та же схема.

Что изменить: проверять пригодность внутри каждой попытки зеркала до признания победителя.

### P2 — нет общего ограничения запросов, закрытая карточка продолжает переводиться

Места: `src/content/index.ts:85`, `src/content/index.ts:131`,
`src/translation/providers/racing.ts:14`, `src/translation/translator.ts:84`.

Закрытие карточки увеличивает `generation` и прячет UI, но не отменяет перевод. Разные тексты
не дедуплицируются. Основной и цитируемый блоки идут одновременно, разные вкладки имеют свои
провайдеры и breaker. Все семь сервисов могут начать работу в течение 950 мс, затем стартуют
оставшиеся зеркала. При достаточно медленных ответах одна попытка короткого блока способна
дать около 18 HTTP-запросов, включая первоначальную авторизацию Bing, ещё до внутренних повторов.

Повторы одинаковы для сетевых сбоев, неправильной языковой пары, 401 и 429; `Retry-After` и jitter
не учитываются. MyMemory особенно чувствителен к лишним отправкам: анонимный лимит — 5000
символов в сутки; с параметром действующего email `de` — 50000. В проекте `de` не передаётся.
[Лимиты MyMemory](https://mymemory.translated.net/doc/usagelimits.php).

Что изменить: общая очередь в background, лимиты параллелизма и частоты по сервисам, отмена
устаревших задач с учётом совместно ожидающих клиентов, классификация ошибок, `Retry-After`,
случайная добавка к backoff. Задержки резервов подбирать по измеренным задержкам провайдеров.

### P2 — пригодность ответа не означает качество перевода

Место: `src/translation/providers/racing.ts:141–151`.

Непустой изменённый текст с сохранёнными маркерами считается успехом. Диагностика: при `ru`
французское `Bonjour tout le monde` принимается. Нет проверки выходного языка, полноты, смысла,
отрицаний или связи чисел с сущностями. Кэш сохраняет такой результат. Сохранение самих чисел
не гарантирует, что переводчик не поменял смысл предложения вокруг них.

Что изменить: проверять язык там, где хватает текста для уверенного определения; добавить корпус
с отрицаниями, суммами, цитатами, сленгом и смешанными языками. Сравнивать движки на этом корпусе.
Не заменять оценку качества грубым требованием «обязательно есть кириллица»: короткие тикеры и
названия бывают корректными без неё. Приоритет движка должен учитывать качество, а не только скорость.

### P2 — строка без переводимых фрагментов может ошибочно считаться отказом

Места: `src/translation/translator.ts:72–80`, `src/translation/providers/racing.ts:145–151`.

`GM $SOL 🚀` полностью маскируется. Если сервис корректно возвращает маркеры и язык `en` либо
не сообщает язык, такой ответ отклоняется как неизменённый. Этот случай воспроизведён с echo-провайдером.
Похожие сообщения, состоящие из тикеров, ссылок или защищённого сленга, не требуют обращения к API.

Что изменить: обнаруживать отсутствие переводимых фрагментов локально и возвращать исходный текст.

### P2 — ошибка цитаты скрывает успешный перевод основного твита

Место: `src/content/index.ts:131–149`.

`Promise.all` объединяет все блоки карточки. Отказ одного переводит всю карточку в состояние ошибки;
готовые результаты остальных не показываются. Особенно неприятно при отдельной цитате на
неподдерживаемом языке или с повреждённым маркером.

Что изменить: состояния и повтор для каждого блока; показывать успешно переведённые части сразу.

### P2 — пользовательский proxy зависит от CORS страниц терминалов

Место: `src/translation/providers/proxy.ts:16`.

В отличие от публичных провайдеров proxy вызывает `fetch` прямо из content script. Сервер должен
разрешать соответствующие origins через CORS, включая preflight для JSON POST. Поэтому произвольный
работающий HTTPS API не становится рабочим резервом только от ввода URL в настройках.
[Документация Chrome о запросах content scripts](https://developer.chrome.com/docs/extensions/develop/concepts/network-requests).

Что изменить: перенести proxy в background, запрашивать разрешение на конкретный origin при настройке,
проверять контракт и соединение. Не расширять права до всех сайтов без необходимости.
Обычный LibreTranslate использует другой контракт, поэтому указать его `/translate` в существующем
proxy-поле без адаптера недостаточно.

### P3 — старый запрос может перезаписать результат принудительного обновления

Место: `src/translation/translator.ts:39–53`.

`force` обходит pending, но обе операции пишут в один cache key. Диагностика: принудительный запрос
завершается первым, старый — позже, и кэш снова содержит старый перевод. Также старый `finally`
без проверки принадлежности удаляет запись другого pending-запроса.
В текущем UI кнопка обновления отключена во время загрузки, что ограничивает частоту этого сценария;
дефект относится прежде всего к контракту Translator при пересечении запросов.

Что изменить: учитывать идентификатор/поколение операции и удалять pending только при совпадении promise.

## Дополнительные ограничения

- Исходный язык и доступные языковые пары не связаны с общим списком 21 языка в настройках.
  Нельзя считать каждый включённый сервис поддерживающим каждую пару. Apertium в этом запуске
  не ответил; его актуальную поддержку `en→ru` по этому запуску установить нельзя.
- Таймеры Translator и RacingTranslationProvider основаны на `abort`, а не на независимом
  завершении promise. Провайдер, игнорирующий сигнал, может нарушить ожидаемый предел ожидания.
  Сейчас runtime-адаптеры самостоятельно отклоняют promise при отмене — это полезная защита.
- В content script заданы три попытки по 12 с и паузы 350/1050 мс: внешний бюджет может достигать
  примерно 37,4 с при соблюдении отмены; отдельные таймеры провайдеров обычно завершают раньше.
- Recovery probe при всех открытых breaker не имеет общей блокировки: несколько запросов могут
  одновременно проверять один сервис. Состояния breaker и кэш не разделяются между вкладками.
- Загрузка настроек в content script не повторяет legacy migration из `shared/settings.ts`; также
  различается обработка `VITE_TRANSLATION_PROXY_URL`. Изменения настроек не подхватываются через
  `storage.onChanged`. При отключении всех провайдеров фабрика бросает ошибку до создания UI.
- Массовая отправка защищённого текста нескольким внешним операторам описана в политике проекта,
  но маскирование терминов не является полной анонимизацией оставшегося текста. Локальный движок
  сокращает и сетевую зависимость, и число внешних получателей.

## Бесплатные решения, которые стоит рассмотреть

Под «лучше» здесь понимается пригодность для повышения надёжности этого расширения. Сравнительный
лингвистический тест этих альтернатив не проводился. Рекомендации — инженерная оценка на основе
контрактов и устройства сервисов, а не обещание лучшего перевода каждой фразы.

| Решение | Бесплатная часть | Роль и ограничения |
| --- | --- | --- |
| Chrome Translator API | Локальный перевод после загрузки языковых пакетов; есть английский и русский | Первый кандидат для уменьшения зависимости от сети. Нужны проверка доступности, подготовка модели по действию пользователя и отдельный контекст выполнения; напрямую в service worker API недоступен. [Документация](https://developer.chrome.com/docs/ai/translator-api) |
| Argos Translate / собственный LibreTranslate | Открытый код и локальное выполнение | Управляемый резерв без квоты внешнего переводчика. Нужны модели и локальный процесс либо свой сервер; серверные ресурсы могут стоить денег. [Argos](https://github.com/argosopentech/argos-translate), [LibreTranslate](https://docs.libretranslate.com/) |
| Azure Translator F0 | 2 млн символов в месяц | Официальный API с ключом; кандидат на основной облачный движок при доступности аккаунта. [Тарифы Microsoft](https://azure.microsoft.com/en-us/pricing/details/translator/) |
| DeepL API Free | 500 тыс. символов в месяц | Официальный резерв с ключом; доступность регистрации зависит от условий сервиса. [Лимиты DeepL](https://developers.deepl.com/docs/resources/usage-limits) |
| Google Cloud Translation NMT | Первые 500 тыс. символов в месяц покрываются ежемесячным кредитом $10 | Документированная альтернатива текущему `client=gtx`. Нужен облачный проект; превышение бесплатного объёма тарифицируется. [Тарифы Google](https://cloud.google.com/products/translate/pricing) |
| TartuNLP + MyMemory | Публичные API без ключа в проверенных вызовах | Пригодны как ограниченные резервы после исправления языка и защиты. У MyMemory малая анонимная суточная квота. [TartuNLP](https://api.tartunlp.ai/translation/docs), [MyMemory](https://mymemory.translated.net/doc/usagelimits.php) |

Для режима «без ключа, регистрации и собственного сервера» я бы сначала реализовал Chrome
Translator API с предварительной подготовкой модели, затем оставил ограниченный облачный резерв.
Обычное наведение не следует считать достаточным действием для первоначальной загрузки модели.
Совместимость контекста расширения и жизненный цикл локального переводчика требуют отдельного прототипа.

При допустимости ключа официальный бесплатный тариф предпочтительнее зависимости от HTML
авторизации Bing или недокументированного Google endpoint. Общий секрет разработчика нельзя
раздавать в исходниках расширения; нужен собственный backend либо индивидуальная настройка ключа.
Бесплатная квота не означает бессрочную гарантию доступности и не обязательно подходит каждому региону.

Добавление зеркал само по себе проблему не решает. Lingva использует Google Translate через scraper,
поэтому не является полностью независимым движком. [Исходный проект Lingva](https://github.com/TheDavidDelta/lingva-translate).
Актуальная официальная страница LibreTranslate перечисляет другие публичные HTTPS-инстансы, чем
все пять зашитых в проекте; часть инстансов требует ключ. Это основание пересмотреть список,
но не автоматически включить все новые адреса без проверки. [Список зеркал LibreTranslate](https://docs.libretranslate.com/community/mirrors/).

## Порядок улучшений

1. Исправить защиту текста, исходный язык и проверку результата внутри гонки зеркал. Сначала добавить
   регрессии для воспроизведённых случаев и реальный набор фраз с маркерами.
2. Довести отмену до конца чтения ответа, отменять устаревшие задачи и ввести общую очередь.
   Различать ошибки квоты, авторизации, неподдерживаемого языка и временной сети.
3. Показывать частичный результат, обрабатывать строки без переводимых фрагментов, защитить force/cache.
4. Прототипировать локальный Chrome API; при необходимости добавить официальный API через
   контролируемый канал. Привести proxy и настройки к одному поведению.
5. Собрать измерения: доля пригодных переводов по языкам, p50/p95 задержки, сохранность защищённых
   значений, число внешних запросов на карточку, причины отказов. Не сохранять текст твитов ради метрик.

Критерии приёмки: отключение любого одного сервиса не ломает перевод при доступном совместимом
резерве; закрытие карточки прекращает ненужную работу; повреждённый ответ одного зеркала не отменяет
другие; при ошибке цитаты виден основной перевод; цифры, ссылки и тикеры сохраняются; исходный
язык не выдумывается; отсутствие сети обрабатывается локальным движком после подготовки моделей.

Даже собственный backend или локальная модель не дают абсолютной безотказности. Они позволяют
устранить конкретные внешние зависимости. Заявлять численную доступность можно только после
длительных измерений; текущих тестов и единичного сетевого снимка для этого недостаточно.
